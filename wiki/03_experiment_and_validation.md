# Experiment and Validation

## Purpose of This Document

This document describes how to validate the pipeline before pointing it at a real Salesforce org. It explains what the experiment tests, what datasets are used, how the validation is structured, and what "good enough" looks like before the tool is considered ready for production use.

---

## What the Experiment Tests

The pipeline has two components that require validation before they can be trusted in production:

**The Classifier** — nine rule-based checks written in Python. These are deterministic and testable directly. The experiment verifies that every check fires on the cases it is designed to catch and does not fire on cases it should leave alone. The rules are described in `02_how_it_works.md`.

**The Prompts** — three prompt templates (`prompt_a_flagged_fields.md`, `prompt_b_uncertain_fields.md` and `prompt_c_reviewed_fields.md`) that instruct the LLM how to handle each classification bucket. These are not deterministic. The experiment surfaces what good and bad output looks like, and the prompts are revised until output quality is consistently acceptable.

The experiment is not about achieving a perfect score. It is about building enough evidence that the Classifier catches the right things and the prompts produce suggestions a human reviewer can actually use.

---

## What the Experiment Does NOT Test

- Real Salesforce connectivity (Tooling API or Metadata API)
- Enterprise LLM infrastructure (Azure OpenAI, AWS Bedrock, Google Vertex AI)
- Write-back to a live org

These are intentionally excluded. The experiment uses synthetic data and a free hosted open-weight model (Groq free tier), so anyone can run and re-run the pipeline without Salesforce credentials, without cost, without special hardware, and without risk to any org. Azure OpenAI is used alongside it to compare models and measure cost.

---

## Experiment Mode vs Production Mode

The experiment runs the **same scripts** as production. There is no separate experiment codebase. Two seams in the pipeline are swapped via `config.yml`:

| Seam | Experiment Mode | Production Mode |
|---|---|---|
| Data input | Reads from a local JSON file (`sf_metadata_raw_training.json` or `sf_metadata_raw_test.json`) | Calls Salesforce Tooling API |
| LLM calls | Free open-weight model on Groq, or Azure OpenAI | Company-approved provider (e.g. Azure OpenAI) |
| Write-back (Script 2) | Dry-run — logs decisions but does not call Metadata API | Calls Salesforce Metadata API |

Everything between those seams — classification logic, routing, prompt assembly, batching, response parsing, review file generation, decision validation — runs identically in both modes.

This means the experiment validates the real pipeline, not a toy version of it.

## Synthetic Datasets — Training and Test

The experiment uses two synthetic datasets. Both are committed to the repository and safe to share publicly. Neither contains real org data.

### Why Two Datasets

The validation approach mirrors standard machine learning practice: a **training set** is used to develop and tune the system, and a held-out **test set** is used only once — to verify that the tuned system generalises to data it has never seen. This separation is essential. If the same dataset is used for both tuning and validation, there is no way to know whether the pipeline works in general or has simply been over-fitted to the examples used during development.

### Training Set — `data/sf_metadata_raw_training.json`

**288 fields — 4 objects × 72 fields each**

Objects: Account, Contact, Opportunity, Case.

The training set is the primary working dataset. It is used during all iterations of classifier development and prompt refinement. Every classification rule is deliberately exercised across multiple field examples, with sufficient variety in phrasing to confirm that the classifier responds to the underlying pattern, not just a single form of wording.

Field composition across all four objects (288 fields, about 72 per object):

| Status | Count | Purpose |
|---|---|---|
| FLAGGED | 78 | Several distinct examples per rule (R1–R5), including multi-rule edge cases where the first-firing rule determines the status |
| UNCERTAIN | 35 | Several distinct examples per rule (R6–R9), including multi-rule edge cases |
| REVIEWED | 158 | Clean fields (genuine good descriptions), near-miss fields (descriptions that look like they might trigger a rule but correctly pass), and subtly vague descriptions left for Prompt C to judge |
| SKIPPED | 17 | System fields not writable via the Metadata API |

These counts are after 21 label corrections made during classifier development, where a label contradicted the rule definitions in wiki 02 (see "Classifier changes during training" below). The set was first written as 63 / 40 / 169 / 16.
| **Total** | **288** | |

Near-miss fields are a critical part of the training set. They are REVIEWED fields deliberately designed to look similar to a failing case — for example a description that contains a known acronym but expands it inline, or a picklist description that is short but still enumerates all values. They test that the classifier does not over-fire.

### Test Set — `data/sf_metadata_raw_test.json`

**144 fields — 4 objects × 36 fields each**

Objects: Account, Contact, Opportunity, Case.

The test set is held out until the classifier and prompts are considered stable on the training set. It is not used during development. It is run exactly once as a final validation check.

Field composition per object (36 fields):

| Status | Count | Purpose |
|---|---|---|
| FLAGGED | 8 | At least one example per rule (R1–R5) on unseen field names and descriptions |
| UNCERTAIN | 6 | At least one example per rule (R6–R9) on unseen field names and descriptions |
| REVIEWED | 20 | Mix of clean, near-miss and subtly vague fields, distinct from training set examples |
| SKIPPED | 2 | System fields |
| **Total** | **36** | |

The test set uses the same objects and the same rule distribution as the training set, but all field names, descriptions, and error phrasings are different. If the classifier and prompts perform well on the test set, the experiment is considered complete.

### Rule Coverage Across Both Datasets

The table below reflects the updated rule numbering. Rules 1–5 produce FLAGGED (Step 1). Rules 6–9 produce UNCERTAIN (Step 2). There is no Rule 10 — see wiki 02.

| Rule | Name | Step | Status |
|---|---|---|---|
| R1 | NULL / Blank | Step 1 | FLAGGED |
| R2 | Echo / Too Short | Step 1 | FLAGGED |
| R3 | Wrong Type Hint | Step 1 | FLAGGED |
| R4 | Undefined Picklist | Step 1 | FLAGGED |
| R5 | Stale or Placeholder | Step 1 | FLAGGED |
| R6 | Too Long (>200 chars and lists its contents) | Step 2 | UNCERTAIN |
| R7 | Jargon Without Context | Step 2 | UNCERTAIN |
| R8 | Contradictory | Step 2 | UNCERTAIN |
| R9 | Audience Mismatch | Step 2 | UNCERTAIN |

## How to Run the Experiment

### Prerequisites

- Python 3.x installed
- Dependencies installed: `pip install -r requirements.txt`
- An LLM API key, either:
  - Groq (free): create a key at https://console.groq.com
  - Azure OpenAI (paid): endpoint, deployment name and key
- `config.yml` created by copying and editing `config.example.yml`

### Phase 1 — Training (iterate until stable)

These steps are repeated as many times as needed until the classifier and prompts meet the Definition of Done criteria on the training set.

1. Set `data_source.experiment_file: data/sf_metadata_raw_training.json` in `config.yml`
2. Run Script 1: `python scripts/01_ingest_classify_send.py`
3. Check `data/sf_classified.json` — verify the classifier is firing correctly (see Classifier Validation below)
4. Open `data/review_queue_{timestamp}.xlsx` — review Tab A and Tab B, approve / edit / reject each row
5. Save the file
6. Run Script 2: `python scripts/02_deploy_approved.py`
7. Review `data/write_log_{timestamp}.xlsx` — no changes will have been written to Salesforce
8. If classifier accuracy or LLM output quality is below the Definition of Done thresholds, revise the relevant classifier logic or prompt file and repeat from Step 2

### Phase 2 — Test (run once, do not iterate)

These steps are run exactly once, after Phase 1 is complete and the classifier and prompts are considered stable.

1. Set `data_source.experiment_file: data/sf_metadata_raw_test.json` in `config.yml`
2. Run Script 1: `python scripts/01_ingest_classify_send.py`
3. Check `data/sf_classified.json` — verify classifier accuracy on unseen fields
4. Open `data/review_queue_{timestamp}.xlsx` — review Tab A and Tab B
5. Save the file
6. Run Script 2: `python scripts/02_deploy_approved.py`
7. Review `data/write_log_{timestamp}.xlsx`
8. Record results in the Test Results section at the end of this document

**The test set must not be used to tune the classifier or prompts.** If results are poor, the correct response is to return to Phase 1, identify the gap, iterate on the training set, and run Phase 2 again from scratch.

## Classifier Validation

After each Script 1 run, verify the classifier is firing correctly by inspecting `data/sf_classified.json`. For each rule, confirm:

- Fields designed to trigger that rule are assigned the expected status (FLAGGED or UNCERTAIN)
- Near-miss fields designed to pass are assigned REVIEWED
- System fields are assigned SKIPPED
- Rules 1–5 never produce UNCERTAIN
- Rules 6–9 never produce FLAGGED
- In multi-rule cases, the first-firing rule determines the status — FLAGGED takes priority over UNCERTAIN because Step 1 is evaluated before Step 2

If a rule misfires — either missing a case it should catch or firing on a case it should not — the classifier logic in `01_ingest_classify_send.py` should be corrected before evaluating LLM output.

## Prompt Evaluation

Once the classifier is confirmed correct on the training set, evaluate the LLM suggestions in the review queue against the criteria below. If output quality is consistently poor for a given rule or category, revise the relevant prompt file and re-run Phase 1.

The mechanical part of these criteria is checked automatically by `python scripts/evaluate_suggestions.py` (add `--failures` to list each failed suggestion). It runs every rewritten or shortened description back through the classifier (a good suggestion comes out `REVIEWED`) and checks length, vague terms, picklist coverage, R6 shortening and the action each prompt asks for. It reports a pass rate per prompt and per rule. "Used to / for / by" is counted as a note, not a failure, because it is acceptable when specific content follows. Specificity and accuracy still need a human reviewer.

The prompt files and golden examples use invented fields that appear in neither dataset, so a suggestion can never be copied from an example of the same field.

### What "Good Output" Means

A suggested description is considered acceptable if it meets all of the following:

**Length**
- Minimum 30 characters
- Maximum 255 characters (hard Salesforce limit)
- Target range for a well-written description: 60–180 characters

**Clarity — no vague terms**

Descriptions are rejected if they contain terms that add no information:
- "used for", "used by", "used to"
- "relevant", "applicable", "various", "related to"
- "information", "data", "details" used without qualification
- "TBD", "N/A", "see above", "ask", "deprecated"

**Specificity**

The description must remain meaningful if the field name and object name are removed. A description that could apply to any field in any system has failed the specificity test.

**Audience**

The description must be written for systems, integrations, and developers — not for end users. It must not contain UI instructions, help text language, or navigational cues.

**Picklist coverage**

If the field is a Picklist or Multi-Select Picklist, the description must reference the values or explain what the values represent.

**Type alignment**

The description must be consistent with the field type. A Checkbox must not be described as if it stores free text. A Date field must not be described as storing a range.

**For UNCERTAIN / R6 (Too Long) specifically**

The LLM suggestion must be shorter than the original and within the 30–200 character target range. The core meaning must be preserved — the LLM must not drop specificity in order to shorten. If the original description is accurate and specific but long, a shortened version that loses key information should be rejected.

## Definition of Done

The experiment is complete when all of the following are true.

### Phase 1 — Training Set

**Classifier**
- All 9 rules fire correctly on the training set
- No field is misclassified on a case explicitly designed to test that rule
- No Step 1 rule (R1–R5) produces UNCERTAIN
- No Step 2 rule (R6–R9) produces FLAGGED
- In all multi-rule cases, the first-firing rule is recorded and the status follows that rule's step

**LLM Output — Tab A (FLAGGED fields)**
- At least 80% of suggestions are approvable without editing, measured twice with the same prompts and model: once **without** org context (where a field's data says nothing, the suggestion must leave the gap to Missing instead of guessing, and 80% must be approvable once the Missing questions are answered) and once **with** an org context file (80% approvable as written). Decided on Day 5: a blank field cannot be described correctly from its name alone
- No suggestion contains vague terms from the rejection list above
- No suggestion exceeds 255 characters
- No suggestion contradicts the field type

**LLM Output — Tab B (UNCERTAIN fields)**
- LLM correctly identifies genuinely acceptable descriptions and does not suggest unnecessary rewrites
- For R6 (Too Long): LLM shortens the description without losing specificity or accuracy
- Where a rewrite is suggested for any other rule, it meets the same quality bar as Tab A

**LLM Output — REVIEWED fields (Prompt C)**
- No suggestion states a fact the input does not support without listing it in `assumptions`; no rewrite removes a fact the original stated
- The subtly vague descriptions in the dataset are rewritten
- Clean and near-miss descriptions are kept; unnecessary rewrites are rare
- Every proposed rewrite meets the same quality bar as Tab A

**Human Review**
- Every row in Tab A and Tab B has a recorded decision (Approve / Edit / Reject)
- No row is left blank
- At least one full review cycle has been completed end-to-end: Script 1 → review file → Script 2 → write log

### Phase 2 — Test Set

**Classifier**
- All 9 rules fire correctly on unseen fields
- No misclassification on any field in the test set

**LLM Output**
- At least 80% of Tab A suggestions are approvable without editing
- At least 80% of Tab B suggestions are approvable without editing (or correctly preserved without change)

**Reproducibility**
- A second person can clone the repository, configure `config.yml`, and run the full experiment — both phases — without any guidance beyond this wiki and the README

## Testing Matrix

Every run of the experiment is one cell in a matrix of four dimensions. Changing one dimension at a time is what makes a result explainable: if two things change between runs, the difference cannot be attributed to either. The matrix also keeps paid runs honest: a cell is only run when it answers a stated question.

### Dimensions

| Dimension | Values | What it isolates |
|---|---|---|
| **Model** | `gpt-oss-120b` on Groq (free, open-weight) · `gpt-5.4-mini` on Azure OpenAI (paid) | How much of the result depends on the model rather than the prompt |
| **Prompt version** | **P1** starting prompts (Day 3) · **P2** invented examples + "Check Before You Answer" (Day 4) · **P3** "Do Not Invent", `assumptions` and `missing` (Day 5) · **P4** ask-don't-write, type-specific Missing, Salesforce knowledge (Day 6, planned) | The effect of instructions, with the input held constant |
| **Context** | **C0** the field's own data only (description, name, type, picklist values, formula, related object) · **C1** + metadata sent with the field (neighbouring fields on the object; label, help text, length, decimals where present) · **C2** + org glossary only · **C3** + metadata and full org context file | Whether a weak suggestion lacked instructions or lacked information |
| **Dataset** | Training (288 fields, iterate freely) · Test (144 fields, run once at the end) | Whether results generalise beyond the data the prompts were tuned on |

Prompt routing (A for FLAGGED, B for UNCERTAIN, C for REVIEWED) is the same in every cell, so every cell reports all three prompts.

### Measures recorded per cell

- **Automatic pass rate** per prompt (`evaluate_suggestions.py`): rule violations only
- **Prompt C rewrites** out of 163 REVIEWED fields: how conservative the model is
- **Assumptions** and **missing** counts (`evaluate_suggestions.py --assumptions`): how much the model guesses and how much it cannot know
- **Human approval rate** on the 40-field sample (`review_sample.py`): the Definition of Done measure. Expensive in reviewer time, so only for cells that decide something
- **Cost** per 1,000 fields sent, and run time

What changed and why:

- **Iteration 1 — examples.** Every example in the prompts and all twelve golden examples were fields from the training set, the golden ones copied word for word. A model shown the answer for a field it is about to process can copy it, so scores on those fields measured memory, not quality. One golden example was even a field the dataset labels R7. All examples were replaced by invented, org-neutral fields that appear in neither dataset. Prompt A and B scores did not drop, so the leak had not been carrying them; the effect is mainly that the training results can now be trusted.
- **Iteration 2 — a final checklist.** A short "Check Before You Answer" list at the end of Prompts A and B (length, acronyms, forbidden terms, picklist values, R6 and R8 specifics) moved Groq's Prompt A from 89% to 96%. The same rules already existed in the system prompt; repeating them as a last step was what worked.
- **Iteration 3 — length versus preservation.** Prompt B told the model to preserve all content when expanding an acronym, so long originals grew past 255 characters. The prompt now says the limit wins. One more field passed; the rest stayed. This is where Groq stopped improving.

Failure patterns that remain:
- **Long originals stay long.** When the original description is already 270–390 characters, both models keep every clause after expanding an acronym, and one model left the text unchanged rather than guess an expansion.
- **Acronyms carried over from the original** ("AE", "CC") are not always expanded.
- **Keyword limits of the classifier.** A correct checkbox rewrite ("Checked when written feedback … has been recorded") still matches the R8 phrase "written feedback". The checker reports what the classifier would do, so a few failures are classifier limits, not bad suggestions.
- **Model differences are in wording, not decisions.** gpt-oss-120b and gpt-5.4-mini chose the same action (rewrite, shorten, keep) for all 271 fields. gpt-5.4-mini follows the forbidden-term list more closely: "used to / for / by" appears in 8 of its Prompt A rewrites against 32 for gpt-oss-120b.

The automatic check is a proxy. The Definition of Done is about suggestions a human would approve without editing, which only the human review sample can measure.

### Invented facts (iterations 4–6)

Prompt C looked like it needed work on *detection* (which reviewed fields to rewrite). It did not: both models rewrote the same 11 of 163 fields, and a hand check of the 152 kept descriptions found none that was vague. Reading the 11 rewrites, rather than scoring them, showed the real defect: they **invented facts**. "Used by the team for internal tracking" became "...triggers internal audit processes". The checker passes such text because invention breaks no rule. The same happened in Prompt A for blank fields, and the single Prompt A example itself invented a process ("Written nightly by the renewal forecasting model…"), which gpt-oss-120b copied almost structurally.

- **Iteration 4** added a "Do Not Invent" section and a final checklist to Prompt C. Invented processes mostly disappeared from gpt-5.4-mini's rewrites.
- **Iteration 5** moved the rule into the system prompt and made every answer return `assumptions`: the claims in the suggestion that the input does not support. The review file shows them as an "Unverified" column. The model overshot: it read "do not invent" as "remove what you cannot verify" and stripped five good descriptions of their own facts.
- **Iteration 6** stated the boundary (the original description is input; keep its claims, do not list them) and added `missing`: the facts a description needs but the input does not give, as questions for the Admin ("Missing" column). Stripping stopped.

The two models read the same rule differently. gpt-5.4-mini mostly leaves an unconfirmed detail out (46 assumptions listed in Prompt A); gpt-oss-120b writes it and lists it (72). Listing works as tracing on both models, as prevention only on gpt-5.4-mini.

### Human review sample

`python scripts/review_sample.py make` draws a fixed, stratified sample from a review queue: 20 Tab A rows (4 per rule), 12 Tab B rows (R6–R9 and Prompt C rewrites) and 8 kept fields. The reviewer decides on the suggestion text only (Approve / Edit / Reject; Agree / Disagree for kept fields) and may add a note. `python scripts/review_sample.py score <file>` prints the rates per tab and rule.

First sample (gpt-5.4-mini, iteration 6 prompts, Day 5):

| Tab | Approve | Edit | Reject |
|---|---|---|---|
| A (20) | 6 (30%) | 10 | 4 |
| B (12) | 5 (+1 rejected only because the sample lacked picklist values) | 4 | 3 |
| C kept (8) | 8 agree | | |

Why Tab A rows were not approved (a row can count twice): an unconfirmed guess left in the text although listed as Unverified (about 8); a fact or caveat of the original dropped, including 3 of 4 R5 rewrites (about 6); meaning that only the org can give, such as what grades A–D stand for (4); Missing asking the wrong question, such as who calculates a score instead of its scale (3); a type mismatch left unfixed (2).

The automatic check passed 98.6% of the same Prompt A suggestions. The two numbers measure different things: the checker sees rule violations, the reviewer sees truth, lost caveats and usefulness. Neither replaces the other.

The reviewer's notes pointed to information the model never receives: the field's neighbours on the same object (a size-notes field only makes sense next to the size fields), org knowledge (what a score's scale and bands are) and Salesforce knowledge (which standard objects already hold SLAs or consents). Day 6 tests these as separate hypotheses: prompt fixes, neighbour fields sent with each field, and an org context file, each measured on the same sample.

### Classifier changes during training

The classifier started at 119/288 (41.3%). The main changes:

- **R6 redefined.** The fields labelled R6 were 210–246 characters long. The long fields labelled REVIEWED were 201–330 characters, so no length threshold could separate the two groups. R6 now fires only when a description is over 200 characters **and** lists what goes into the field (see wiki 02, Rule 6). This rule is provisional: it matches how the synthetic set was written and should be re-checked on more realistic data.
- **R4 skips placeholder text**, so a picklist described as "TODO" or "TBD" is recorded as R5.
- **Whole-word matching** for placeholder tokens and picklist values. "ask" had matched inside "task", "to do" inside "to document", and a picklist value "A" had matched every letter a.
- **R7 allow-list** extended with currency codes and common trade terms (CHF, VIP, VP, SMB, IVR, clothing sizes). ID format codes such as `RA-XXXXXXXX` are no longer treated as jargon.
- **New R3/R8 patterns** for Text, Date and Currency fields.
- **21 labels corrected** where the label contradicted the rule definitions in wiki 02. Most were picklists whose description ignores the values (R4), or fields whose unexplained acronym had been hidden by the old length-only R6.
